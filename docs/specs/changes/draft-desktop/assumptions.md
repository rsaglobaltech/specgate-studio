# Assumptions — draft-desktop

What the brief does not say, chosen so the scenarios can be tested. Each is to
confirm by the person reviewing the draft.

| # | Assumption | Used in | Why | Status |
|---|---|---|---|---|
| A1 | The cold start of the brief's example (0.8 s) is measured from launching the app to sprich's Home answering a click, on a Mac with no Node installed; it sits inside the workbench's budget (visible < 300 ms, interactive < 1 s, draft-workbench REQ-035) | REQ-151, SCN-451 | The brief's example; ADR-0002's budgets | confirmed |
| A2 | The sidecar is the core host built as a Node 22 single executable application (ADR-0002), started by the Tauri shell with a session token, listening on 127.0.0.1 on a free port; closing the window ends the sidecar's process tree — a process group on macOS and Linux, a Job object on Windows | REQ-151, SCN-451, SCN-452 | ADR-0002; runtime-environments rule 2; cross-platform process trees | confirmed |
| A3 | **One window per project is not written in the brief**: it is drafted from the sidecar rule and the core host's "one core host per open project" (REQ-001); the brief could say it in its own rule. Opening a project already open focuses its window; the example folders are `~/mvp/specgate-studio` and `~/mvp/sprich-platform/sprich`, the latter opened from the Recent list (REQ-026) | REQ-152, SCN-453, SCN-454 | Asked for by the person who owns the studio when this draft was requested | confirmed |
| A4 | macOS, staged: **now** the .dmg is unsigned — ad-hoc signed only, which Apple silicon needs to run it — and the release links to documented "Open anyway" steps (on macOS 15 and later: open the app, then System Settings → Privacy & Security → Open Anyway; the docs also give `xattr -dr com.apple.quarantine` for when macOS says the app "is damaged"). **Once** the owner has an Apple Developer Program membership with a Developer ID Application certificate and an App Store Connect API key, the same release workflow adds `codesign` with the hardened runtime (the sidecar with the JIT entitlements V8 needs), `notarytool` and stapling; checked with `spctl --assess --type execute`. Separate arm64 and x64 .dmg files, not one universal file, to stay under 80 MB | REQ-153, REQ-157, SCN-455, SCN-466 | Q1: unsigned now, signed when the certificate exists, the same pipeline gains the step | confirmed |
| A5 | Windows, staged: **now** the .msi is unsigned and the release links to documented SmartScreen steps ("More info" → "Run anyway"). **Once** the owner has a code-signing certificate (a cloud signing service or a certificate on a hardware token: private keys of new code-signing certificates must live in hardware since 2023), the same workflow signs the .msi, the app and the sidecar with Authenticode and an RFC 3161 timestamp; checked with `Get-AuthenticodeSignature`. SmartScreen may still warn a new publisher until it builds reputation | REQ-154, SCN-456, SCN-467 | Q1, as for macOS | confirmed |
| A6 | Linux: the .AppImage and the .deb signed with a GPG key the project creates and publishes (no paid account), as detached `.asc` signatures on the release; tested on Ubuntu 24.04 and Fedora 41 | REQ-155, SCN-457, SCN-458 | The brief asks for signed installers on Linux too | confirmed |
| A7 | Releases are published on GitHub Releases of `rsaglobaltech/specgate-studio`, built by a release workflow on macOS, Windows and Linux runners, where the signing secrets live; nothing is signed on a developer's machine. Building the desktop app needs Rust (rustup), which the CI runners install | REQ-153 … REQ-157 | runtime-environments, release row; ADR-0002 | confirmed |
| A8 | Auto-update is Tauri's updater: a `latest.json` on the release, each update signed with the updater's own key (a free key, separate from the Apple and Windows certificates, kept as a CI secret), checked on start; so auto-update works while the installers are still unsigned. An update the app downloads itself carries no quarantine flag, so macOS shows no "Open anyway" step for it. The versions 0.7.0 and 0.7.1 are examples. On Linux the .AppImage updates itself; the .deb is updated by installing the new .deb, which the studio offers as a download | REQ-156, SCN-459, SCN-460, SCN-461 | Tauri 2's updater; Q3 | confirmed |
| A9 | The update waits while a build or any write command runs (REQ-006), and says so; installing has a "?" and a notice (from which version, to which, restart to apply) in English and Spanish in the help catalog (draft-help REQ-061 … REQ-065) | REQ-156, SCN-459, SCN-460 | The studio explains itself; a build must not be cut | confirmed |
| A10 | Idle is 60 s with sprich open and no action; memory is the resident memory of every process of the app (the window, its webview processes, the sidecar and its children); "installer" is each downloadable file (.dmg per architecture, .msi, .AppImage, .deb). In the browser, the 200 MB is the host's process, the browser's own memory not counted. Measured in CI on each release | REQ-157, SCN-462, SCN-463 | The brief gives the numbers, not how they are measured | confirmed |
| A11 | `specgate-studio serve` run for a project the desktop app has open joins that project's core host instead of starting a second one (core host REQ-001); the browser and the desktop window get the same events (REQ-005), so an answer given in one shows in the other | REQ-158, SCN-464, SCN-465 | ADR-0001: the same UI over the same host | confirmed |
| A12 | The example's REQ-030 and Q2 are sprich's, as phase 2's drafts use them (draft-build-live A1) | REQ-156, REQ-158, SCN-460, SCN-465 | Values the drafts already use | confirmed |
| A13 | No specgate command is needed for this module: the desktop app runs the same core host, which talks to specgate through `SpecgatePort` as in the browser | REQ-151 … REQ-158 | ADR-0003 | confirmed |
| A14 | The warnings that must not show are the systems' own: "cannot be opened" and "unidentified developer" from Gatekeeper on macOS, "unknown publisher" from Windows when an installer is not signed. With unsigned installers these warnings do show, and the documented steps get past them | REQ-153, REQ-154, SCN-455, SCN-456, SCN-466, SCN-467 | What an unsigned installer shows today | confirmed |
| A15 | One release workflow builds every installer; signing is a step in it that runs when its secrets exist (macOS: Developer ID certificate and notarization key; Windows: the signing certificate or service) and is skipped, saying so in the release notes, when they do not. The "Open anyway" and SmartScreen steps are a page in the docs that each unsigned release links to; it is removed from a platform's release once that platform is signed | REQ-153, REQ-154, SCN-466, SCN-467 | Q1: unsigned for now, signed when the accounts exist, the same pipeline gains the step | confirmed |
| A16 | The installers are signed in the owner's own name, as an individual developer (Apple Developer Program individual membership; a Windows certificate issued to a person); moving to the organization rsaglobaltech later needs its verification (D-U-N-S for Apple, business validation for Windows) and changes only the certificates the workflow uses. The owner's exact name as shown by macOS and Windows is the one on the certificates | REQ-153, REQ-154, SCN-455, SCN-456 | Q2: the owner's own name now, rsaglobaltech later | confirmed |
| A17 | The update is offered when the studio starts, installed when the Developer accepts, and applied on the next restart; while a build or a write command runs, installing waits and says so. Declining it offers it again on the next start | REQ-156, SCN-459, SCN-460 | Q3: offered on start, applied on restart, never during a build | confirmed |
